# Bangumi 列表接口字段事实（v0 vs p1）

> 实测日期 **2026-09-19**（含 URL、状态码、样本原文）。凡标「实测」的都有脚本与缓存可复现。
> 复现脚本：`tools/probe-list-fields.mjs`、`tools/probe-v0-tags.mjs`、`tools/probe-v0-round2.mjs`、`tools/probe-v0-health.mjs`、`tools/coverage-union.mjs`
>
> 👉 **要落地实现，看 [bangumi-v0-api-guide.md](./bangumi-v0-api-guide.md)** —— 那份是「怎么用」的完整方案
> （请求 / 字段 / 清洗四步 / 成品词表 / 覆盖率 / 最小实现 / 9 条坑）；本文只记「事实长什么样」。

## 一句话结论

**`api.bgm.tv/v0/subjects` 的列表项同时返回 `tags`（全量投票词，≤30 个）和 `meta_tags`（服务端结构化摘要）**；
`tags` 与「详情接口」返回的 30 个 tag **逐字节一致** ⇒ **列表一次请求就够，不需要再逐条补拉详情。**

## 1. 端点对照

| | v0（推荐） | p1 |
|---|---|---|
| URL | `https://api.bgm.tv/v0/subjects` | `https://next.bgm.tv/p1/subjects` |
| 必填 | `type=2`（动画） | `type=2` |
| 分类 | `cat=1`(TV) / `5`(WEB) / `2`(OVA) / `3`(剧场版) | 同 |
| 时间 | `year=` 可单独用；`&month=` 可精确到月 | 同 |
| 分页 | **`limit`（上限 100）+ `offset`** | `page`（每页固定 24） |
| `total` 语义 | **总条数** | **总页数** |
| 单页上限 | 100（`limit=200` → **HTTP 400**，实测） | 24（固定） |
| 列表项 tag 字段 | **`tags` + `meta_tags`** | 仅 `metaTags` |
| UA / Referer | **不校验**（裸请求 200，实测） | 不校验 |
| 响应体积 | 112 KB / 24 条（含全量 tags） | 15.6 KB / 24 条 |
| 耗时 | 3.4~8.8 s | 1.6~5.0 s |
| 字段风格 | 下划线 `name_cn` / `total_episodes` | 驼峰 `nameCN` + `info` 字符串 |

> 取同样信息的**总成本**：TV 2026 全年 334 条 → v0 **4 次请求**（每次 100 条，含全量 tags）；p1 **14 次请求**，且 tags 还得逐条补拉。

## 2. 两个 tag 字段的区别（★ 核心）

### `tags` — 用户投票的全量词
```json
{ "name": "漫画改", "count": 446, "total_count": 870571 }
```
- `count` = **该条目**上的票数；`total_count` = **全站**该 tag 的总票数
- 长度不固定（实测取值 3 / 6 / 8 / 22 / 30），**上限 30**；空数组也合法
- **与 `p1/subjects/{id}` 详情接口返回的 tags 逐字节一致**（实测 3/3 完全相同）⇒ 详情补拉是多余的
- 混着噪声：`2026年1月`（年月）、`MAPPA`（制作公司）、`地狱乐`（作品名）、`2026`（年份）、`3D`/`TVA`（技术词）、`佐藤雅子`（人名）

### `meta_tags` — 服务端筛出的结构化摘要
- 成分 = **平台**（TV/WEB/OVA/剧场版）+ **地区**（日本/中国/欧美/美国）+ **来源**（漫画改/原创/小说改）+ **题材**（奇幻/战斗/日常），剔掉年月/公司/人名/作品名/技术词
- **不是「按票数取前 N」** —— 实例：黄金神威 tags 票数 Top1 是 `漫画改(241)`，`meta_tags` 却以 `TV` 开头；地狱乐 tags 里 `MAPPA(528)` 票数第 2 却不在 `meta_tags` 里
- ⚠️ **带重复 bug（实测 60 条里 21 条）**：如 `["TV","TV","日本","日本","奇幻","奇幻","漫画改","漫画改","战斗","战斗"]` —— 同一个词重复 2~6 次，且**不保证相邻成对**

```js
// 必须去重后再用
const meta = [...new Set(item.meta_tags || [])];
```
- p1 的 `metaTags`（驼峰）**无重复**，去重后与 v0 的 `meta_tags` **8/8 一致**（实测）

## 4. 这对手头项目的意义

1. **详情补拉机制可以整个删掉** —— 列表 `tags` 就是详情数据，`cfg.tagDetail`（off/empty/fill）与 `fetchDetailTags` 的存在前提消失了。
2. **题材命中率显著提升** —— 只用 `meta_tags` 时 T1（题材）命中 57.3%；用 `meta_tags ∪ tags` 是 **74.2%**（2026 四类 744 条实测）。原因就是「梅比乌斯之尘」这类：题材词只在 `tags` 里。
3. **但覆盖率的天花板不在词表** —— `meta_tags` 里的词 **100% 落在既有白名单覆盖范围内**（实测"全未中 ≡ 字段为空"，31 = 31）。所以**加词永远提不上去**，真正的缺口是「两个字段都为空」的条目。

### 覆盖率（2026 · 口径 `meta_tags ∪ tags`，744 条）

| 类型 | 条数 | T1 | T1+T2 | T1+T2+T3 | 全未中 |
|---|---|---|---|---|---|
| TV | 334 | 82.9% | 92.5% | 98.5% | 1.5% |
| WEB | 262 | 70.2% | 83.2% | 96.6% | 3.4% |
| OVA | 7 | 85.7% | 100% | 100% | 0% |
| 剧场版 | 141 | 60.3% | 79.4% | 98.6% | 1.4% |

> ⚠️ 此前"T1+T2+T3 = 100%"的结论**只是 TV 一类的样本**，不能推广到四类。
> 无 tag 的条目集中在 **WEB**：欧美网络动画、短片、剧场版真人 4D（`SEALOOK` / `史努比露营` / `吃豆人` / `Thomas & Friends` / `Lilo & Scratch`）—— 这些在 Bangumi 上没人投中文 tag，**任何白名单都救不了**。
> `影视改`（Tier2）2026 零命中，可考虑删。

## 5. 不要重复踩的坑

1. **别从一个端点推断另一个端点** —— "列表项没有 tags"只对 p1 成立。
2. **一次故障 ≠ 永久故障** —— 2026-09 上旬 v0 带 query 全线 502，**现已恢复**（裸请求 200、连续 8/8 成功）。用之前重测一次。
3. **v0 的 `meta_tags` 必须去重**，p1 的不用（但去重无害）。
4. **`limit` 上限是 100** —— 试探到 400 才知道；超了直接 400 而非截断。
5. **`total` 语义相反**：v0 是条数、p1 是页数 —— 用错会导致翻页死循环或提前停止。
6. **大 `limit` 体积线性增长** —— 100 条约 450 KB；移动端/慢网要权衡，或退回分页。

## 6. 三次元（真人影视）分类映射 —— 2026-09-20 实测

### 6.1 `type` / `cat` 组合

| 组合 | 含义 | 实测 |
|---|---|---|
| `type=2` `cat=1/2/3/5` | 动画 TV / OVA / 剧场版 / WEB | 服务端即分类，**平台纯净** |
| `type=6` `cat=1` | **日剧** | 375 条（2024 全年），platform 全为「日剧」 |
| `type=6` `cat=2` | **欧美剧** | 133 条（2024 全年），platform 全为「欧美剧」 |
| `type=6` `cat=3` | **华语剧** | 179 条（2024 全年），platform 全为「华语剧」 |
| `type=6` `cat≥4` | —— | **一律 HTTP 400**（cat 5…14 逐个试过） |

> ★ 关键：**「电影」不是一个 `cat`**。带 `cat=1/2/3` 扫描 2024 全年时，`platform="电影"` 命中 **0 条** —— 电影完全不在这些 cat 里。

### 6.2 `platform` 字段（列表项自带）

`type=6` 的 `platform` 全集**只有 8 种**：

```
日剧 / 欧美剧 / 华语剧 / 电影 / 演出 / 其他 / 电视剧 / 综艺
```

`type=2` 的 `platform` 与 `cat` 一致：`TV / OVA / 剧场版 / WEB`。

### 6.3 电影的正确取法

**不带 `cat`**（即 `type=6&year=&month=`）→ 返回该 type **所有平台**的条目 → 前端按 `platform` 过滤。

实测各年电影量（不带 cat，逐月累加）：

| 年 | 电影条数 |
|---|---|
| 2026 | 214 |
| 2025 | 330 |
| 2024 | 235 |
| 2023 | 182 |

**`year+month` 在带 cat / 不带 cat 两种形态下都生效** —— 不带 cat 拉回来的条目 `date` 全部落在所查月份内（电影实测）。故月份分组无需额外处理。

### 6.4 ⚠️ 没有「韩剧」分类

`鱿鱼游戏`、`黑暗荣耀` 等韩剧的 `platform` 是 **`电视剧`** —— 一个**混合容器**（与部分美剧/台剧等混放），只能靠 `tags` / `meta_tags` 里的「韩国」区分。因此：

- **不要**做「韩剧 = 某个 cat/platform」的映射，不存在；
- 靠 tag 过滤会漏（tag 非 100% 覆盖）也会误收；
- 本项目的选择是**放弃韩剧 tab**。

### 6.5 过滤 + 分页的坑 ★

带前端过滤时，**整页可能全部不匹配**（电影只占全量的 1/6）。此时：

```js
// ❌ 错：第一个「恰好没有电影」的页就 break，后面全漏
if (filteredItems.length === 0) break;

// ✅ 对：看过滤前的原始页长度
if (rawLen === 0) break;
```

同理，若用「本次 push 进结果的条数 === 0」判停也会误判。**判停必须基于原始分页数据，不能基于过滤后的结果。**

## 8. 只为「封面 + 集数」的速度对比（2026-09-21 实测 · 2026 年 7 月新番）

问题：选 v0 优先的代价是响应体积 12 倍。那**如果不看 tag 覆盖**，只要封面图和集数呢？

样本 `type=2&cat=1&year=2026&month=7`（TV 新番，v0 报 79 条），每侧 3 轮取中位。

### 8.1 结果

| 指标 | v0 `api.bgm.tv` | p1 `next.bgm.tv` | 胜 |
|---|---|---|---|
| 请求数 | **1** | 3 | v0 |
| 传输字节 | 592.5 KB | **49.1 KB** | p1（12.06×） |
| 墙钟耗时（中位） | 9669 ms | **3584 ms** | **p1（2.70×）** |
| 条目数 | **79** | 63 | **v0** |
| 封面命中 | 79/79 | 63/63 | 平 |
| 集数命中 | 65/79（原生 `eps`） | 58/63（需解析 `info`） | v0 略胜 |

**结论：慢网下 p1 快 2.7 倍，但 p1 少 20% 条目、且集数不在字段里。** 见 8.3 / 8.5。

### 8.2 ★★ 封面档位：两条通路的档位命名**不一致**

`images` 同为 5 档，但档位对应关系不同（各抽 6 条，映射完全稳定）：

| 档位 | v0 | p1 |
|---|---|---|
| `large` | 原图 | 原图 |
| **`common`** | **r/400** | **r/400** |
| **`medium`** | **r/800** | **r/200** |
| `small` | r/200 | r/100 |
| `grid` | r/100 | **r/100x100（方形裁剪）** |

> ⚠️ **勘误（v1.6.4 修正）**：`grid`(p1) 曾被本文档记为「原图」，**实为 `r/100x100` 方形裁剪**。
> 误记原因：判档正则写成 `\/r\/(\d+)\//`，而 `r/100x100` 里 `\d+` 后面接的是 `x` 不是 `/`
> ⇒ 匹配失败，落进了「无 `r` 段 = 原图」的兜底分支。**判档正则必须容忍 `x<H>` 后缀**：
> `\/r\/(\d+)(?:x\d+)?\/`。

同一张图（#255209）各档真实下载（串行实测）：

| 档位 | 尺寸参数 | 字节 | 耗时 |
|---|---|---|---|
| `large` | 原图 | 863.5 KB | 8233 ms |
| `common` | 400 | **71.0 KB** | 603 ms |
| `medium` | 800 | **241.7 KB** | 2336 ms |
| `small` | 200 | 20.5 KB | 490 ms |
| `grid` | 100 | 6.2 KB | 1457 ms |

⇒ 脚本那行 `cover: imgs.medium || imgs.common || ...` 在这两条通路上取到**差 12 倍**的图：
**v0 通路拿 r/800（241.7 KB/张），p1 通路拿 r/200（20.5 KB/张）**。

卡片列宽是 `minmax(132px, 1fr)`（窄屏 104px），2× DPR 只需 ~300px 宽 ⇒ **`medium` 在 v0 上是 6 倍冗余，在 p1 上又偏小**。
**只有 `common`（r/400）在两条通路上都等于 400** ⇒ 想行为一致就得用 `common`。

量级对比（7 月 79 张）：

| 取图方案 | 单张 | 79 张合计 |
|---|---|---|
| 现状 v0 通路（`medium`=r/800） | 241.7 KB | **18.6 MB** |
| 改用 `common`（r/400） | 71.0 KB | **5.5 MB**（−70%） |
| `small`（r/200） | 20.5 KB | 1.6 MB |

⇒ **接口响应总共才 592 KB，封面图是它的 31 倍**。真要提加载速度，改封面档位的收益远大于换接口。

**✅ 已落地（v1.6.3）**：抽出 `pickCover(imgs)` 统一两条通路，取值顺序改为
`common → medium → large → small`，并对 `imgs` 为 `null/undefined` 加了兜底（原写法直接取属性会抛）。
E2E 新增 **4.9 段**断言封面档位，防止日后回退。

⚠️ 顺带发现：`small` 与 `grid` 同样不对齐（`small`：v0 r/200 / p1 r/100；`grid`：v0 r/100 / p1 **r/100x100 方形**）
⇒ **除 `common` 外没有一档是两边一致的**，别改用其它档位。

### 8.2b ★★ `/r/<N>/` 是**离散档位**，只有 5 档可用（v1.6.4 实测）

拿同一张 `common` URL 换掉宽度段重下：

| 宽度 | HTTP | 字节 | 结论 |
|---|---|---|---|
| `r50` | **400** | — | ❌ 不支持 |
| `r100` | 200 | 6.2 KB | ✅ |
| `r150` | **400** | — | ❌ 不支持 |
| `r200` | 200 | 20.5 KB | ✅ |
| `r300` | **400** | — | ❌ 不支持 |
| `r400` | 200 | 71.0 KB | ✅ |
| `r600` | 200 | 147.7 KB | ✅ |
| `r800` | 200 | 241.7 KB | ✅ |

⇒ **可用档位严格只有 100 / 200 / 400 / 600 / 800**，任意宽度会 400 ⇒ 做「封面质量」选项时必须限定这几个值。

另加一条 `withCoverWidth` 形状检查（含 `r/100x100` 剥离）。

### 8.3 ★ p1 有隐藏的「收藏数门槛」，整体丢掉约 20% 条目

同口径下 v0 79 条 / p1 63 条，**只有 v0 有的 16 条**。按 `rating.total` 分布：

| | 条数 | 收藏数 min | 中位 | max |
|---|---|---|---|---|
| 仅 v0 有 | 16 | 0 | 8 | **50** |
| 两边都有 | 63 | **69** | 521 | 4775 |

**两个区间完全不重叠**（50 < 69）⇒ p1 存在门槛 ≈ 51~69 收藏。丢掉的多是当月刚开播还没积累收藏的新番/冷门番
（例：地球大好き！きっくん、喜羊羊与灰太狼之破界山海诀、暗芝居 第十七季、Mickey Mouse Clubhouse+）。

⚠️ 这解释了为什么 p1 不能当等价数据源 —— 它是有偏采样。

### 8.4 v0 的体积大头**不是** tag

79 条 592.5 KB（7.50 KB/条）的字段分解：

| 字段 | 总字节 | 占比 | 卡片用得上？ |
|---|---|---|---|
| `infobox` | 334.4 KB | **57.9%** | ✗ 制作人员名单 |
| `tags` | 102.8 KB | 17.8% | ★ |
| `summary` | 86.3 KB | 14.9% | ✗ 简介 |
| `images` | 27.1 KB | 4.7% | 是 |
| `rating` | 8.7 KB | 1.5% | 是 |
| 其余 15 个字段 | 17.9 KB | 3.1% | 多数用不上 |

- **用不上的字段合计 426.9 KB = 72.1%**
- **`tags + meta_tags` 只占 17.9%** ⇒ **即便完全不要 tag，v0 也只能省 17.9%**

⇒ 所以「为 tag 而选 v0」付的钱，其实是**为 `infobox` 付的**。v0 不支持字段选择，592 KB 是硬成本。

### 8.5 ★ 网络条件（结论的前提，别忽略）

对 v0 端点做 `limit=1/10/50/100` 序列并线性拟合 `t = a + b·bytes`：

| limit | 字节 | 耗时 |
|---|---|---|
| 1 | 9.1 KB | 3930 ms |
| 10 | 96.0 KB | 5469 ms |
| 50 | 418.0 KB | 12061 ms |
| 100 | 592.5 KB | 8286 ms |

⇒ **固定延迟 ≈ 4677 ms**（DNS+TLS+RTT+服务端），**带宽 ≈ 101 KB/s**。

即**本机到 Bangumi 的链路很慢**（约 100 KB/s，疑似代理线路）。在这个前提下「体积即时间」，所以 p1 胜。
若换成 1 MB/s 的链路，v0 的 592 KB 只需约 0.6 s，**1 个请求反而可能追平 p1 的 3 个 RTT**。
⇒ 换网络环境请重测，别把本次数字当绝对结论。

另外 p1 的 3 个请求总共只花 3584 ms（并发 2）< v0 单请求的 4677 ms 固定延迟
⇒ **`next.bgm.tv` 的后端本身也比 `api.bgm.tv` 快**，两者服务端延迟不对等。
