# 二级白名单设计方案（可移植）

> 一套「从接口真实词表里筛标签」的方法与成品词表，供任何需要在卡片上展示**流派/题材标签**的项目复用。
> 本文档中的词表与代码**不依赖本项目**，可直接搬走。

---

## 1. 要解决的问题

卡片上一个 2 个槽位的 tag 区，怎么决定放什么词？

常见错误是**凭直觉写白名单**（"热血、治愈、搞笑、异世界、催泪……"）。这样写出来的表在真实数据上几乎全是死词：
本项目最初的 60 词白名单里，**39 个词在列表接口里从来没出现过**，等于白占位置；同时又漏掉了真正高频的词。

正确顺序是：**先拿到接口真实词汇表与频次 → 再分类 → 再筛选**。

## 2. 数据来源与字段事实（Bangumi）

| 项 | 结论 |
|---|---|
| 列表接口 | `https://next.bgm.tv/p1/subjects?type=2&cat={1TV/5WEB/2OVA/3剧场版}&year=&month=&page=N` |
| 分页 | 参数名是 **`page`**（`limit`/`offset`/`perPage`/`pageSize` 全部被忽略）；每页固定 **24** 条；`total` 是**总页数** |
| 列表里的 tag 字段 | **只有 `metaTags`**（列表项没有 `tags` 字段），类型 `string[]` |
| 每条的 tag 个数 | 不固定，**1~8 个**（2023 实测 289 条：1~2 个 56 条 / 3~4 个 102 条 / 5+ 个 131 条，平均 **3.98**） |
| 它的本质 | **人工挑选的摘要**（平台 + 地区 + 来源 + 1~2 个内容词），**不是"票数 Top N"**。反例：某条目详情里 `MADHouse(2292票)` 比 `TV(1865票)` 高，列表却只给了 `TV` |
| 完整 tag | 只能逐条拉详情 `GET /p1/subjects/{id}`（返回 **30** 个 `{name,count}`）；**没有批量接口**（`&full=1/&detail=1/&tags=1` 均被忽略） |
| CORS | 列表接口**无 CORS 头** ⇒ 浏览器里必须走 `GM_xmlhttpRequest` 或自建代理 |

### 2.1 关键事实：**这是一个受控小词表**

四年样本（2023–2026，共 **937 条**）的 `metaTags` 去重后**只有 53 个不同词**：

| 年份 | 条数 | 词汇表大小 |
|---|---|---|
| 2026 | 148 | 45 |
| 2025 | 241 | 48 |
| 2024 | 259 | 52 |
| 2023 | 289 | 52 |
| **并集** | **937** | **53** |

**这条事实决定了整套方案**：白名单不是"从无限词汇里挑"，而是**从这个 53 词的小表里做取舍** ——
所以**覆盖率的天花板由「数据里有没有词」决定，而不是由词表大小决定**；反过来，词表可以全量写死、几乎不会漂移。
2026 全四类实测：T1+T2 覆盖 **86.8%**，开 Tier3 到 97.8%（详见 §3.2）。

## 3. 分层设计

按「信息价值」把真实词汇表分成三层，**层号即显示优先级**：

| 层级 | 语义 | 词数 | 作用 |
|---|---|---|---|
| **Tier1 题材** | 奇幻 / 战斗 / 恋爱 … | 27 | **首选显示**（同层内按票数先后） |
| **Tier2 来源·受众** | 漫画改 / 原创 / 少年向 … | 12 | Tier1 没词时兜底；Tier1 只有 1 个词时**补满槽位** |
| **Tier3 平台·地区** | TV / WEB / 日本 / 中国 … | 10 | 最后兜底（开 = 覆盖率 ~98%，关 = ~87%）。代价是卡上出现「TV/日本」⇒ **默认关**，理由见 §3.2 |
| 排除 | 短片集、短片（**形式**）、R18（**分级**） | 3 | 不是题材，显示出来没信息量 |

### 3.1 显示优先级算法（三级兜底 + 一二级拼接）

```
候选 = tags（用户投票全量，按 count 降序）++ meta_tags（服务端摘要）→ 去重
out  = [Tier1 命中…] + [Tier2 命中…]        // 题材永远排在前面，二级用于补满槽位
if (out.length < n && 开启Tier3) out += [Tier3 命中…]
return out.slice(0, n)
```

- 例：`[奇幻, 漫画改]` → `奇幻 漫画改`（题材在前、补满 2 格）
- 例：`[TV, 日本, 小说改]` → `小说改`（Tier1 无词 → 用 Tier2 兜底）
- 例：`[TV, 日本]` → 开关开：`TV 日本`；开关关：**空**
- **不要**写成"只显示最高层命中的那一层"：那样 `[奇幻, 漫画改]` 只剩 1 个词，槽位浪费。

### 3.2 覆盖率实测

**口径（2026-09-19 更正）**：候选词池 = **`tags ∪ meta_tags`** —— v0 列表接口**一次请求就给全**，
既不需要拉详情，也不该只看 `meta_tags`（后者是服务端摘要，会为塞平台/地区而丢掉题材词）。

| 评估年 | 样本 | 仅 Tier1 | Tier1+2 | Tier1+2+3 |
|---|---|---|---|---|
| 2026（全四类） | **744** | 74.2% | **86.8%** | 97.8% |

分类型（2026，Tier3 关）：

| 类型 | 条数 | 仅 Tier1 | Tier1+2 |
|---|---|---|---|
| TV | 334 | 82.9% | 92.5% |
| WEB | 262 | 70.2% | 83.2% |
| OVA | 7 | 85.7% | 100% |
| 剧场版 | 141 | 60.3% | 79.4% |

结论：**"不出现空 tag"确实只能靠 Tier3 兜底**，靠追加题材词永远差最后一截。
**但别急着开 Tier3** —— 空卡只有三种成分（2026 全四类实测）：

| 空卡原因 | 条数 | 占比 | 能不能救 |
|---|---|---|---|
| 两字段都是空数组 | 13 | 1.7% | **不能**。数据不存在，拉详情也是空 |
| 词池里只有平台/地区词 | 82 | 11.0% | 开 Tier3 能填，但填进去是「WEB / 剧场版 / 中国 / 日本」 |
| 词池里有白名单外词 | **3** | 0.4% | 理论上能补词，但这 3 条的未命中词是 `Albert.Birney`、`三浦莉希`、`山下清悟` —— **全是人名** |

⇒ **补词收益为零**（加人名只会污染词表），而 11% 的兜底词比空着更没信息量 ⇒ **Tier3 默认关，宁缺毋滥**。
⇒ 同时**不要做详情补拉**：详情返回的 `tags` 与列表的 `tags` 逐字节一致，一个空卡都救不了。
⇒ 复现命令：`node tools/empty-card-audit.mjs 2026`（读缓存，零请求）。接口调用细节见 [bangumi-v0-api-guide.md](./bangumi-v0-api-guide.md)。

### 3.3 边际贡献度（判断"这个词能不能删"）

定义：某词**作为条目里唯一命中白名单词**出现的次数。`= 0` ⇒ 它与别的白名单词永远共现 ⇒ **删掉不改变覆盖率**，只是显示少了一种可能。

> **口径说明**：下面这组数字是在「仅 `meta_tags`」的**旧口径**下测的（评估年 2024）。
> 换成 `tags ∪ meta_tags` 后未重测 —— 边际贡献度会随口径变化。重测命令：
> `node tools/whitelist-tiers.mjs 2026,2025,2024,2023 --eval=2024`。

实测零贡献词 9 个（旧口径）：`后宫 惊悚 耽美 少年向 青年向 女性向 少女向 同人 乙女`
**最小核心白名单 = Tier1 24 词 + Tier2 6 词 = 30 词**，该口径下四年覆盖率与全集**逐位相同**。

> 注意：零贡献 ≠ 该词无用。它们是"锦上添花"（能丰富卡片内容），只是不影响"有没有 tag"这个指标。本方案**保留全集**，只在需要极简表时用核心版。

## 5. 移植到其他项目的步骤

1. **换接口**：把 `tools/tag-freq.mjs` 的 URL/分页参数改掉，跑一遍拿到**真实词汇表 + 频次**（本项目落盘为 `tools/.e2e-anime-out/tag-cache-{year}.json`，二次运行零请求）。
2. **看词表规模**：
   - 去重后是几十个词 ⇒ 受控词表，可以**全量人工分类**（本项目即此情形）；
   - 上千个词 ⇒ 先按频次取头部（覆盖 95% 出现次数），再分类，其余按规则丢弃。
3. **按语义分类**：题材 / 来源 / 受众 / 平台 / 地区 / 形式 / 分级；**未归类词要告警**（新词往往就是"需要补充"的候选）。
4. **算边际贡献度**：找出「零贡献词」，决定保留（丰富显示）还是删掉（极简）。
5. **实测覆盖率**：分别报 `仅Tier1` / `Tier1+2` / `Tier1+2+3`，**不要只报一个数**——三档对应三种产品取舍。
6. **定 Tier3 开关默认值**：本项目定案是**关**（卡上出现「TV/日本」比空着更没信息量）；要"每张卡都有标签"再开。
7. **不要实现详情补拉**：先验证「详情接口返回的 tag」是否与「列表项里的 tag」逐字节相同（本项目实测**相同**）—— 相同就纯属浪费请求，且救不了空卡。
8. **先查空卡成分再优化词表**：把空卡分成「字段全空 / 只有平台·地区词 / 白名单外词」三类（见 §3.2），只有第三类值得补词；本项目第三类只有 3 条、且全是人名 ⇒ 直接放弃补词。

工具（本项目内可直接复用）：

```bash
node tools/tag-freq.mjs 2024,2025        # 逐年词频 + 白名单对照，带缓存
node tools/tag-freq-merged.mjs 2026,2025 # 多年合并频次总表
node tools/whitelist-tiers.mjs 2026,2025,2024,2023 --eval=2024   # 分层 + 边际贡献 + 覆盖率
node tools/tag-tier-audit.mjs 2023       # 逐条审计：每条命中哪级哪些词 + 未命中词频次（+ HTML 视图）
```

## 6. 参考实现

```js
const T1 = new Set([/* 27 题材 */]);
const T2 = new Set([/* 12 来源·受众 */]);
const T3 = new Set([/* 10 平台·地区 */]);

const rawTagNames = v => Array.isArray(v)
  ? v.map(t => (typeof t === 'string' ? t : t && t.name)).filter(s => typeof s === 'string')
  : [];

/** 分级筛选：题材优先 → 来源/受众补位 → （可选）平台/地区兜底 */
function pickTags(names, n = 2, useTier3 = false) {     // ★ 默认关 Tier3
  const uniq = [...new Set(rawTagNames(names))];
  const pick = set => uniq.filter(t => set.has(t));
  let out = [...pick(T1), ...pick(T2)];
  if (out.length < n && useTier3) out = out.concat(pick(T3));
  return out.slice(0, n);
}

/** 是否命中题材词 —— 判断这张卡有没有"内容词"（v0 通路下不再用于触发补拉） */
const hasGenreTag = names => rawTagNames(names).some(t => T1.has(t));
```

> ⚠️ `rawTagNames` 记得**去重**：v0 的 `meta_tags` 有服务端重复 bug（`["TV","TV","日本","日本",…]`）。
> 另外**候选词池**要由 `tags` 与 `meta_tags` 并集而来，且 `tags` 先按 `count` 降序 —— 完整写法见
> [bangumi-v0-api-guide.md §六](./bangumi-v0-api-guide.md#六可复制的最小实现)。

### 6.1 详情补拉：**本项目最终没有采用**（其他项目也别做）

早期版本的思路是「列表 tag 不够 ⇒ 逐条拉 `/v0/subjects/{id}` 补」。**已被实测推翻**：

- 详情接口返回的 `tags` 与**列表项**的 `tags` **逐字节一致**（实测 3/3）⇒ 一个字节都没多；
- 两个字段都空的条目，详情也是空的 ⇒ **补拉救不了任何一张空卡**；
- 代价却是每张卡片一次额外请求（本项目实测约 33% 的卡片会触发）。

所以：**只要用的是 `api.bgm.tv/v0/subjects`，详情补拉就没有存在意义。**
只有在「被迫走 p1（列表项不带 `tags`）」时才需要考虑它，写法：

```js
const need = items.filter(it =>
  mode === 'empty' ? it.tags.length === 0                        // 只补空白
                   : (!hasGenreTag(it.tagPool) || it.tags.length < 2));  // 没题材词或槽位没满
```
- **串行 + 间隔**（本项目 320ms），按 `id` 长期缓存（tag 基本不变）；
- 结果刷新时用"更好才替换"的判据：**先比有没有题材词，再比词数**。

## 7. 陷阱清单

| # | 陷阱 | 说明 |
|---|---|---|
| 1 | **凭直觉写白名单** | 必须有频次数据。本项目 60 词里 39 词零命中 |
| 2 | **只用 `meta_tags` 一个字段** | 它是服务端摘要（**不是**票数 TopN），会为塞平台/地区而丢掉题材词 ⇒ 必须与 `tags` **取并集** |
| 3 | **忘了给 `meta_tags` 去重** | 它有服务端重复 bug（`["TV","TV","日本","日本",…]`，60 条里 21 条中招） |
| 4 | **只报一个覆盖率数字** | 必须拆 `仅Tier1 / T1+2 / T1+2+3`，否则看不出取舍 |
| 5 | **用一个端点推断全局** | 本项目曾因 `/v0/subjects` 全线 502 断言"这接口不行"、改走 p1；同日晚间再测**已完全恢复**。接口会变，结论要写日期 |
| 6 | **用"某词从未出现"下结论** | 换一年数据就可能出现（"39 词结构性永不出现"被 2024 数据推翻）；准确说法是**零边际贡献** |
| 7 | **做详情补拉** | 详情返回的 tag 与列表项**逐字节一致** ⇒ 纯浪费请求，且救不了空卡（两字段都空的条目详情也是空） |
| 8 | **加词就想凑到 99%** | 最后 10% 缺的不是题材词，而是"词池里只有平台/地区词"；只有 Tier3 能补 —— 而本项目定案是**不加**（唯一的补词候选全是人名，见 §3.2） |
| 9 | **让白名单去驱动"要不要补拉"** | 这套判据只在被迫走 p1 时才有意义；v0 通路下补拉已整个关闭 |
| 10 | **数据源故障当成代码 bug** | 接口整段 502 是服务端问题 ⇒ 要有兜底通路与冷却 |
| 11 | **只信计算样式** | 颜色/可见性必须验**真像素**（本项目曾出现"面板背景全透明""浮层被自己的隐藏规则藏掉"这类 DOM 看不出的问题） |

- 词表与算法：`bili-anime-replace.user.js` 的 `TAG_T1 / TAG_T2 / TAG_T3` + `pickTags()` / `hasGenreTag()`

- 开关：设置面板「无题材/来源词时用平台·地区兜底（Tier3）」与「详情补拉」—— **两个都默认关**
- 审计与复现工具：`tools/tag-freq*.mjs`、`tools/whitelist-tiers.mjs`、`tools/tag-tier-audit.mjs`、`tools/coverage-union.mjs`、`tools/empty-card-audit.mjs`
- 接口调用方案：[bangumi-v0-api-guide.md](./bangumi-v0-api-guide.md)；字段事实：[bangumi-list-api-facts.md](./bangumi-list-api-facts.md)
- 原始数据：`tools/.e2e-anime-out/tag-cache-{2023..2026}.json`、`full-tags-2026.json`（744 条）、`whitelist-tiers-*.tsv`
